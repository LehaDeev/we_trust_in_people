# Торговля

## Авто-режим

Scheduler запускается как фоновый asyncio-task вместе с ботом.
Каждые `TRADING_INTERVAL_SECONDS` выполняется один тик:

1. Проверяются открытые позиции — срабатывание **стоп-лосс** или **тейк-профит**
   — в экс-дивидендный день SL-порог автоматически снижается на размер дивиденда,
   чтобы предсказуемый гэп не вызвал ложное срабатывание
2. Инкрементально загружаются завершённые свечи из Tinkoff API в БД (только новые,
   с момента последней сохранённой, пауза `TRADING_CANDLE_UPDATE_PAUSE_SECONDS` между тикерами);
   Redis-кеш свечей и сигналов инвалидируется — модель работает на актуальных данных
3. Получаются ML-сигналы для всех тикеров
4. **SELL-сигнал** — позиция закрывается только если чистый P&L > 0 после комиссий и НДФЛ
   _(SL/TP исполняются всегда — это управление риском)_
5. **BUY-сигнал** — позиция открывается при `confidence ≥ threshold`, где threshold —
   per-ticker значение из `ml/weights/best_threshold_{ticker}_{version}.json` (подбирается
   Optuna при обучении). При отсутствии файла используется глобальный `TRADING_CONFIDENCE_THRESHOLD`.
   Также требуются: свободные слоты и достаточный баланс.

## Биржевые TP/SL ордера

После открытия позиции бот **немедленно** выставляет два стоп-ордера:

| Тип | Ордер | Срок действия |
|---|---|---|
| TP | Стоп-ордер SELL (`STOP_ORDER_TYPE_TAKE_PROFIT`) | `GOOD_TILL_CANCEL` — срабатывает когда цена ≥ TP-уровня |
| SL | Стоп-ордер SELL (`STOP_ORDER_TYPE_STOP_LOSS`) | `GOOD_TILL_CANCEL` — срабатывает когда цена ≤ SL-уровня |

**Почему оба — стоп-ордера (не лимитный TP):**
Лимитный SELL-ордер немедленно блокирует/резервирует акции в портфеле. При этом, когда SL-стоп
срабатывает, биржа не может создать рыночный ордер — акции уже заблокированы под TP лимитный.
Результат: ошибка «Недостаточно бумаг в портфеле», позиция не закрыта.
Стоп-ордера хранятся на стороне брокера и **не блокируют акции** до момента срабатывания —
OCO-конфликт устранён.

**Логика каждого тика:**

1. В начале тика один раз получаются все активные стоп-ордера (`get_stop_order_ids`).
   Лимитные ордера запрашиваются только если есть позиции с legacy `tp_order_id`.

2. Для каждой открытой позиции:
   - Если `tp_stop_order_id` есть в БД, но **отсутствует** в стоп-ордерах:
     - Цена ≥ `take_profit_price` → TP сработал: отменяется SL стоп-ордер, позиция закрывается.
     - Цена < `take_profit_price` → стоп-ордер отменён биржей: TP перевыставляется.
   - Если `sl_stop_order_id` есть в БД, но **отсутствует** в стоп-ордерах:
     - Цена ≤ `stop_loss_price` → SL сработал: отменяется TP стоп-ордер, позиция закрывается.
     - Цена > `stop_loss_price` → стоп-ордер был отменён биржей: SL перевыставляется.
   - Если `sl_stop_order_id` не был выставлен при открытии (сбой API) → выставляется в текущем тике.
   - Если ни `tp_stop_order_id` ни `sl_stop_order_id` нет в БД (позиция создана вручную или восстановлена):
     - Выставляются оба стоп-ордера (TP + SL). Оба принимаются биржей круглосуточно.
     - Если не удалось → фолбэк: сравнение текущей цены с уровнями SL/TP.

**Backward compatibility — legacy `tp_order_id`:**
Позиции, открытые до обновления (с `tp_order_id` — лимитный ордер), продолжают работать:
- Если лимитный TP исчезает из активных → попытка проверить через `get_order_state()`.
  При истечении — мигрируется на стоп-TP: `tp_order_id` очищается, `tp_stop_order_id` заполняется.
- OrderWatcher stream продолжает матчить legacy `tp_order_id` для мгновенного обнаружения.

**Утренний тик (9:50 МСК):** `_morning_tp_loop` запускает полный `_tick()` ровно в 9:50 МСК
каждый день — TP/SL перевыставляются за 10 минут до открытия основной сессии.

**Идентификаторы** ордеров хранятся в таблице `trades`:
- `tp_stop_order_id` — ID стоп-ордера TAKE_PROFIT (новый формат, не блокирует акции)
- `tp_order_id` — ID лимитного TP-ордера (legacy, только для старых позиций)
- `sl_stop_order_id` — ID стоп-ордера STOP_LOSS

## Мониторинг ордеров в реальном времени (OrderWatcher)

`trading/order_watcher.py` запускается как фоновая задача рядом с планировщиком.
Два параллельных механизма:

| Механизм | Для чего | Задержка |
|---|---|---|
| gRPC `trades_stream` | Legacy TP (лимитный ордер `tp_order_id`, старые позиции) | мгновенно |
| Polling каждые `TRADING_ORDER_POLL_SECONDS` | SL и новый TP (`tp_stop_order_id`) | ≤ `TRADING_ORDER_POLL_SECONDS` сек |

**Почему SL и новый TP не ловятся через stream:**
Стоп-ордер при срабатывании создаёт новый рыночный ордер с другим `order_id`.
ID этого ордера нигде не сохранялся — матчинг через stream невозможен.
Вместо этого polling проверяет:
- `sl_stop_order_id` исчез из активных + цена ≤ SL → SL сработал.
- `tp_stop_order_id` исчез из активных + цена ≥ TP → TP сработал.

**Взаимодействие со scheduler:**
Scheduler продолжает проверять позиции каждые 30 минут (ML-сигналы + новые позиции).
OrderWatcher только закрывает существующие позиции быстрее.
Двойное закрытие исключено: перед записью в БД проверяется `trade.status == 'OPEN'`.

## Ручной режим

Переключение прямо из бота кнопкой «Переключить на ручной».
Доступны кнопки **Купить** и **Продать**:
- **Покупка**: проверяет баланс, размер лота и лимит позиций; показывает прогноз P&L при TP/SL
- **Продажа**: показывает расчёт чистого P&L → требует подтверждения

## Расчёт P&L

```
entry_total  = цена_входа  × лоты × размер_лота
exit_total   = цена_выхода × лоты × размер_лота
gross_pnl    = exit_total - entry_total
комиссии     = entry_total × commission_pct + exit_total × commission_pct
НДФЛ         = max(0, (gross_pnl - комиссии) × tax_pct)
net_pnl      = gross_pnl - комиссии - НДФЛ
```

**Цена выхода в уведомлении** — фактическая цена исполнения (`fill_price`) от биржи,
полученная после подтверждения сделки. `breakdown` пересчитывается от `closed_trade.exit_price`
(а не от `current_price` на момент выставления ордера), поэтому все цифры в уведомлении
согласованы с записью в БД.

`TRADING_STOP_LOSS_PCT` и `TRADING_TAKE_PROFIT_PCT` задаются как **целевой чистый** результат.
Бот сам пересчитывает нужный gross-уровень цены. Пример при `SL=3%, TP=5%`, комиссии 0.05% (тариф «Трейдер») и НДФЛ 13%:

```
TP = 5.0% чистых → цена должна вырасти на ~5.87% (gross, с учётом комиссии и НДФЛ)
SL = 3.0% чистых → цена должна упасть  на ~2.90% (gross, с учётом комиссии на выход)
Breakeven: gross > +0.10% (= 2 × 0.05% комиссии)
```

Анализ частоты срабатывания по 21 000+ часовых свечей SBER/GAZP/LKOH (lookahead=4h):
- TP=5.0%: срабатывает редко — крупное движение за 4 часа
- SL=3.0%: срабатывает ~0.5–1.2% — редко, защита от крупных движений
- ~93% сделок закрываются по сигналу планировщика (следующий тик — SELL/HOLD), не по SL/TP

## Динамические SL/TP на основе ATR

При `TRADING_DYNAMIC_SLTP_ENABLED=true` уровни SL/TP вычисляются индивидуально
для каждой сделки на основе текущей волатильности инструмента:

```
atr_ratio = ATR(14) / close  (последний завершённый бар)

sl_pct = clamp(atr_ratio × TRADING_ATR_SL_MULTIPLIER,
               TRADING_ATR_MIN_SL_PCT,
               TRADING_ATR_MAX_SL_PCT)

tp_pct = sl_pct × TRADING_ATR_RISK_REWARD_RATIO
tp_pct = max(tp_pct, sl_pct)   # TP не ниже SL (минимальный RR = 1:1)
```

`atr_ratio` передаётся из `predict_signal()` в поле `"atr_ratio"` результирующего словаря.
При `atr_ratio = 0` (признак не вычислен) или `TRADING_DYNAMIC_SLTP_ENABLED=false` —
используются фиксированные `TRADING_STOP_LOSS_PCT` / `TRADING_TAKE_PROFIT_PCT`.

### Типичные значения для MOEX тикеров (1h свечи)

| Тикер | atr_ratio (типичный) | SL при ×2.0 | Диапазон после clamp |
|---|---|---|---|
| SBER, GAZP (ликвидные) | 0.007–0.010 | 1.4%–2.0% | 1.5%–2.0% (min clamp 1.5%) |
| LKOH, GMKN (средние) | 0.009–0.013 | 1.8%–2.6% | 1.8%–2.6% |
| FEES, HYDR (низкая ликв.) | 0.010–0.020 | 2.0%–4.0% | 2.0%–4.0% |
| Кризисная волатильность | 0.020+ | 4.0%+ | 4.0% (max clamp) |

**Примеры** при `ATR_SL_MULTIPLIER=2.0`, `ATR_RISK_REWARD_RATIO=1.5`, `min=1.5%, max=4%`:
- `atr_ratio=0.008` → SL=1.6%, TP=2.4%
- `atr_ratio=0.010` → SL=2.0%, TP=3.0%
- `atr_ratio=0.015` → SL=3.0%, TP=4.5%
- `atr_ratio=0.020` → SL=4.0% (max), TP=6.0%

Breakeven win rate при RR=1.5:1 составляет ~43% (с учётом комиссии 0.05% и налога 13%).

### Логирование

При каждом открытии позиции в лог выводятся `sl_pct` и `tp_pct`:
```
Позиция открыта ticker=SBER sl_pct=0.024 tp_pct=0.04 stop_loss=... take_profit=...
```

При наличии нескольких открытых позиций по одному активу всегда продаётся

## Фильтр рыночного режима

При `TRADING_REGIME_FILTER_ENABLED=true` BUY-сигнал проходит дополнительную проверку
на режим рынка перед открытием позиции. Фильтр применяется **после** расчёта лотов.

### Определение режима (market_regime)

`market_regime` вычисляется в `compute_features()` из уже посчитанных индикаторов:

```
+1 (аптренд):   SMA20 > SMA50  И  close > SMA20  И  (ADX > порог  ИЛИ  aroon_up > aroon_down)
-1 (даунтренд): SMA20 < SMA50  И  close < SMA20  И  (ADX > порог  ИЛИ  aroon_down > aroon_up)
 0 (флет):      все остальные случаи
```

`ML_REGIME_ADX_THRESHOLD` (по умолчанию 20) — порог ADX для разграничения тренда и флета.
Для часовых свечей рекомендуется 20; для дневных — 25.

### Логика фильтра

| Режим | Условие | `TRADING_REGIME_FILTER_MODE=soft` | `TRADING_REGIME_FILTER_MODE=hard` |
|---|---|---|---|
| +1 (аптренд) | Тренд вверх | лоты без изменений | лоты без изменений |
| 0 (флет) | Нет тренда | лоты × `TRADING_REGIME_FLAT_MULTIPLIER` | lots = 0, BUY пропускается |
| -1 (даунтренд) | Тренд вниз | lots = 0, BUY пропускается | lots = 0, BUY пропускается |

**Режим `soft` (рекомендуется)**: в даунтренде BUY полностью заблокирован; в флете лоты
уменьшаются вдвое (`TRADING_REGIME_FLAT_MULTIPLIER=0.5`) — часть сигналов сохраняется.

**Режим `hard`**: BUY открывается только в явном аптренде; в флете и даунтренде — блокировка.

### Backward compatibility

- `TRADING_REGIME_FILTER_ENABLED=false` — фильтр полностью отключён, поведение как до внедрения.
- Если `market_regime` отсутствует в словаре сигнала — fallback `1` (аптренд, не блокировать).

### Настройки

| Переменная | Описание | По умолчанию |
|---|---|---|
| `ML_REGIME_ADX_THRESHOLD` | Порог ADX: ниже = флет, выше = тренд (для часовых свечей) | `20.0` |
| `TRADING_REGIME_FILTER_ENABLED` | Включить фильтр | `true` |
| `TRADING_REGIME_FILTER_MODE` | `soft` = снижать лоты в флете; `hard` = блокировать в флете и даунтренде | `soft` |
| `TRADING_REGIME_FLAT_MULTIPLIER` | Множитель лотов в флете при `soft`. `0.5` = вдвое меньше; `0.0` = блокировать; `1.0` = без ограничений | `0.5` |

## Фильтр подтверждения объёмом

BUY-сигнал открывает позицию только если объём последнего бара превышает SMA_20(объём) на заданный коэффициент:

```
volume_ratio = volume_last_bar / SMA_20(volume)

BUY + confidence >= threshold + volume_ratio >= TRADING_VOLUME_MIN_RATIO → открыть позицию
BUY + volume_ratio < TRADING_VOLUME_MIN_RATIO → пропустить (лог: "объём ниже порога")
```

Повышенный объём подтверждает что за движением стоят крупные участники, а не случайное колебание.
Рекомендуемые значения: `1.0` (отключён) → `1.1` (мягкий) → `1.3` (умеренный) → `1.5` (строгий).

## Управление размером позиции (Position Sizing)

### Метод: Fixed Fractional Risk

При `TRADING_POSITION_SIZING=fixed_risk` (рекомендуется) число лотов рассчитывается
так, чтобы потеря при срабатывании SL составляла ровно `TRADING_RISK_PCT_PER_TRADE × balance`,
независимо от цены тикера и текущей волатильности.

```
риск_на_сделку  = balance × TRADING_RISK_PCT_PER_TRADE
стоимость_позиции = риск_на_сделку / sl_pct
лотов           = floor(стоимость_позиции / (цена × lot_size))
лотов           = clamp(лотов, 1, TRADING_MAX_LOTS_PER_TRADE)
```

Метод органично связан с ATR-based SL: при высокой волатильности SL шире → лотов меньше;
при тихом рынке SL уже → лотов больше. Риск остаётся постоянным в рублях.

**Примеры расчёта** при балансе 200 000 ₽, риске 1% (`TRADING_RISK_PCT_PER_TRADE=0.01`), SL=2%:

| Тикер | Цена | Размер лота | Риск (₽) | Стоимость позиции | Лотов |
|---|---|---|---|---|---|
| SBER | 300 ₽ | 10 | 2 000 ₽ | 100 000 ₽ | 33 |
| GAZP | 150 ₽ | 10 | 2 000 ₽ | 100 000 ₽ | 66 |
| PLZL | 13 500 ₽ | 1 | 2 000 ₽ | 100 000 ₽ | 7 |

Потеря при срабатывании SL для всех трёх позиций одинакова: ≈ 2 000 ₽ (1% от 200 000 ₽).

При `TRADING_POSITION_SIZING=fixed_lots` — всегда `TRADING_LOTS_PER_TICKER` лотов
(старое поведение, обратная совместимость).

### Почему не Kelly Criterion

Критерий Келли требует точных оценок win_rate и payoff ratio из истории сделок.
При отсутствии накопленной статистики (cold-start проблема) estimation error превышает
сам edge стратегии. Использование predicted P&L как proxy для edge ненадёжно:
регрессор даёт rank-оценки, а не абсолютные вероятности.
Kelly применим после накопления 100+ закрытых сделок — до тех пор Fixed Fractional
является стандартом в алготрейдинге (Van Tharp, «Trade Your Way to Financial Freedom»).

### Масштабирование по уверенности сигнала (Confidence Scaling)

При `TRADING_CONFIDENCE_SCALING_ENABLED=true` применяется **третий слой** position sizing —
после `compute_lots()` и фильтра рыночного режима.

**Три слоя sizing в порядке применения:**

```
1. compute_lots(balance, price, lot_size, sl_pct)
       ↓
2. _apply_regime_filter(lots, market_regime)
       ↓
3. apply_confidence_scaling(lots, confidence)
       ↓
   lots_final → open_position()
```

`confidence` = предсказанный net P&L из `predict_signal()` (доля от вложений, 0.008 = 0.8%).
Это НЕ вероятность — регрессор выдаёт rank-оценку ожидаемой доходности.
Типичный диапазон BUY-сигналов MOEX 1h: **0.003–0.025** (0.3%–2.5%).

**Методы масштабирования:**

| Метод | Входные данные | Поведение |
|---|---|---|
| `tiered` (рекомендуется) | confidence, tier_low, tier_high, mult_low/mid/high | 3 уровня → 3 фиксированных множителя. Простота + интерпретируемость |
| `linear` | confidence, tier_low (baseline), mult_low/high | `mult = clamp(confidence / tier_low, mult_low, mult_high)`. Непрерывный, но чувствителен к масштабу confidence |
| `kelly` | confidence, tier_low (proxy edge), mult_low/high | `mult = clamp(0.5 × confidence / tier_low, mult_low, mult_high)`. Half-Kelly снижает агрессивность при неточном edge |

**Логика tiered (дефолт):**

```
confidence < TRADING_CONFIDENCE_TIER_LOW:               lots × TRADING_CONFIDENCE_MULT_LOW   (0.5×)
TIER_LOW <= confidence < TRADING_CONFIDENCE_TIER_HIGH:  lots × TRADING_CONFIDENCE_MULT_MID   (1.0×)
confidence >= TRADING_CONFIDENCE_TIER_HIGH:             lots × TRADING_CONFIDENCE_MULT_HIGH  (1.5×)
```

Результат всегда `max(1, int(lots × mult))` и не превышает `TRADING_MAX_LOTS_PER_TRADE`.

**Примеры** при базовом расчёте `compute_lots()` = 4 лота:

| confidence | Уровень | Метод tiered | Итог |
|---|---|---|---|
| 0.003 | слабый | 4 × 0.5 = 2.0 → 2 лота | ↓ |
| 0.008 | средний | 4 × 1.0 = 4.0 → 4 лота | = |
| 0.018 | сильный | 4 × 1.5 = 6.0 → 6 лотов | ↑ |

**Backward compatibility:** при `TRADING_CONFIDENCE_SCALING_ENABLED=false` (дефолт)
функция возвращает лоты без изменений — поведение идентично отсутствию фичи.
При `lots = 0` (блокировка режим-фильтром) масштабирование не применяется.

### Настройки

| Переменная | Описание | По умолчанию |
|---|---|---|
| `TRADING_POSITION_SIZING` | `fixed_risk` (рекомендуется) или `fixed_lots` | `fixed_risk` |
| `TRADING_RISK_PCT_PER_TRADE` | Доля баланса под риском на сделку (`0.01` = 1%) | `0.01` |
| `TRADING_MAX_LOTS_PER_TRADE` | Жёсткий максимум лотов (защита от ошибок) | `10` |

## Дивидендная защита стоп-лосса

Когда компания выплачивает дивиденды, акция предсказуемо падает примерно на
сумму дивиденда в экс-дивидендный день. Чтобы это не вызвало ложное срабатывание
стоп-лосса, бот применяет защитный сдвиг:

```
effective_sl = stop_loss_price - dividend_per_share
```

### Индивидуальное окно защиты

Для каждой акции автоматически вычисляется среднее количество дней, за которые
дивидендный гэп исторически закрывался (данные за 5 лет, дневные свечи):

1. Получить все дивидентные события из Tinkoff API
2. Для каждого — найти первый день, когда цена вернулась к 98 % от уровня до гэпа
3. Среднее (ceiling) сохраняется в PostgreSQL (`assets.dividend_gap_days`)
4. Пересчёт — раз в 30 дней или при первом добавлении актива

### Приоритет источников

| Приоритет | Источник | Как задать |
|---|---|---|
| 1 (высший) | Ручное переопределение | `TRADING_DIVIDEND_OVERRIDE=SBER:45,GAZP:90` |
| 2 | PostgreSQL (`assets.dividend_gap_days`) | Авто или `UPDATE assets SET ...` |
| 3 | Глобальный фоллбэк | `TRADING_DIVIDEND_PROTECTION_DAYS=1` |

## Портфель

При открытии раздела «Портфель» отображается:
- Общая стоимость счёта (активы + свободный остаток)
- Свободный рублёвый баланс
- Итоговая стоимость по каждой категории

Четыре кнопки для перехода в список активов:

| Кнопка | Тип инструмента | Показывает |
|---|---|---|
| 📈 Акции | `share` | Тикер, кол-во шт., ср. цена покупки, текущая цена, P&L |
| 📄 Облигации | `bond` | Тикер, кол-во шт., ср. цена покупки, текущая цена, P&L |
| 🏦 ETF | `etf` | Тикер, кол-во шт., ср. цена покупки, текущая цена, P&L |
| 💱 Валюта | `currency` | Валюта, объём, ср. цена покупки, текущая цена, P&L |

Тикер определяется по FIGI из таблицы `assets` в БД.
Для активов вне отслеживаемого списка отображается FIGI[:10].
