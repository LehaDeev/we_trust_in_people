# ML-система

## Архитектура ансамбля

Для каждого тикера обучается отдельный `RankEnsemble` — ансамбль с z-score нормализацией:

```python
RankEnsemble(
    estimators=[
        ("lgbm", LGBMRegressor(objective="quantile", alpha=..., ...)),  # квантильная регрессия
        ("et", ExtraTreesRegressor(...)),                                 # MSE, среднее P&L
        ("hist_gbm", HistGradientBoostingRegressor(loss="absolute_error", ...)),  # MAE, медиана
    ],
)
# predict() → weighted_average(z-score_lgbm, z-score_et, z-score_hist_gbm, weights=_weights)
# z-score_i = (pred_i - train_mean_i) / train_std_i
# _weights = softmax(spearman_i / ML_ENSEMBLE_WEIGHT_TEMP)  — вычисляется на OOS-фолде
```

**Почему `RankEnsemble`, а не `VotingRegressor`:** простое среднее (VotingRegressor) подавляется моделью
с наибольшим диапазоном предсказаний и разбавляется моделями с константными предсказаниями.
Z-score нормализация устраняет оба эффекта: каждая модель вносит равный вклад в ранговый сигнал,
а модели с std≈0 автоматически получают нулевой вклад.

### Адаптивные веса ансамбля (Val-fold Spearman Weighting)

После финального обучения ансамбля каждая базовая модель оценивается на **последнем walk-forward фолде** (OOS):

1. Клонируем базовую модель (копируем только гиперпараметры, не веса).
2. Обучаем клон на `train_idx` фолда — модель не видела `val_idx`.
3. Считаем `spearman_i = Spearman(model_clone.predict(X_val), y_val)`.
4. Применяем softmax с температурой `T = ML_ENSEMBLE_WEIGHT_TEMP`:
   ```
   w_i = exp(spearman_i / T) / sum(exp(spearman_j / T))
   ```

**Гарантии корректности:**
- Веса вычисляются на **val_idx** — данных, которые финальный ансамбль не видел в том же фолде.
- Нет утечки: `_cv_spearman_score` делает независимый fit на каждом фолде.
- Backward compatibility: старые `.pkl` без поля `_weights` используют равные веса.
- Вырожденный случай (все Spearman ≤ 0 → все веса равные через `set_weights` фолбэк) защищён.

**Влияние температуры `ML_ENSEMBLE_WEIGHT_TEMP`:**

| Значение | Эффект |
|---|---|
| `0.1` | Winner-takes-all: лучшая модель получает почти весь вес |
| `1.0` | Умеренная дифференциация (рекомендуется) |
| `100.0` | Практически равные веса (поведение как до внедрения фичи) |

Веса логируются в structlog после каждого обучения тикера.

`StandardScaler` не используется: деревья инвариантны к монотонным преобразованиям признаков.

**Почему регрессия, а не классификация:** классификатор (BUY/SELL/HOLD) дискретизирует непрерывный P&L через
произвольный порог, создаёт дисбаланс классов (~88% отрицательный P&L) и требует `class_weight="balanced"`.
Регрессор напрямую предсказывает ожидаемый net P&L, устраняя рассогласование между целью обучения и метрикой HPO.

**Почему три разных objective:** с ~88% отрицательных целей MAE/MSE сходятся к медиане/среднему (~−0.006),
что делает все предсказания отрицательными и лишает BUY-сигналов. Три разных функции потерь дают три разных
взгляда на распределение P&L — разнообразие предсказаний снижает ошибку ансамбля:
- **LightGBM `quantile`**: `alpha` тюнируется Optuna в [0.7, 0.95]. Предсказывает alpha-й квантиль P&L.
  При alpha=0.88 → LGBM предсказывает 88-й перцентиль P&L. Для действительно хороших баров прогноз положительный.
- **ExtraTrees (MSE)**: среднее P&L. Стабилен на больших выборках, низкая корреляция с LGBM.
- **HistGradientBoosting (MAE)**: медиана P&L. Sklearn-нативная реализация, быстрее ET, нечувствительна к выбросам.

**Почему ExtraTrees, а не RandomForest:** ET использует случайные пороги разбиений вместо
поиска лучшего — корреляция с LightGBM значительно ниже, ансамбль получает реальное разнообразие.

Весь ансамбль сохраняется в одном `.pkl` файле.

> **Важно:** после изменения набора признаков (`features.py`) или структуры ансамбля
> необходимо запустить `python -m scripts.train_model --force-tune` —
> Optuna подберёт гиперпараметры под новый набор признаков.

## Per-ticker отбор признаков

Обучение проходит в **два прохода**:

1. **HPO (Optuna)** — гиперпараметры трёх моделей подбираются на **всех 54 признаках**.
   Деревья сами игнорируют слабые признаки через регуляризацию (`min_split_gain`,
   `min_impurity_decrease`, `l2_regularization`) — отбор на этом этапе не нужен.

2. **Проход 1** — зондовый `fit` ансамбля с HPO-параметрами на всех 54 признаках.
   Вычисляется нормализованная importance (per-model к сумме = 1, затем усредняется).
   Признаки с `avg_importance < ML_FEATURE_IMPORTANCE_THRESHOLD` отбрасываются.

3. **Проход 2** — оптимизация порога уверенности (Optuna, без утечки) и финальный `fit`
   только на отобранных признаках. Список сохраняется в `features_{ticker}_{version}.json`.

Каждый тикер получает **свой** набор признаков:

```
features_SBER_v2.json  → ["OBV", "cmf_20", "vwap_ratio", ...]   # 32 признака
features_LKOH_v2.json  → ["high_252_ratio", "MACD_hist", ...]   # 40 признаков
features_YDEX_v2.json  → ["hist_vol_20", "donchian_pct", ...]   # 37 признаков
```

Инференс загружает `features_{ticker}_{version}.json` автоматически — изменений в коде не требуется.

## Стратегия кросс-валидации: WalkForwardSplit

HPO (Optuna) и финальная оценка ансамбля используют **роллинговую CV** вместо расширяющегося окна (`TimeSeriesSplit`).

### Почему не TimeSeriesSplit

`TimeSeriesSplit` из sklearn реализует **расширяющееся окно**: каждый следующий фолд добавляет все предыдущие данные к обучающей выборке. Для MOEX это создаёт две проблемы:

1. **Утечка меток (label leakage):** метки последних барóв каждого train-окна вычислены по P&L через `lookahead=4` свечи вперёд — первые 4 бара val-окна уже участвовали в вычислении этих меток. Без gap=lookahead оценка Spearman завышена.

2. **Устаревшие данные:** структурный разрыв MOEX (февраль 2022) кардинально изменил рыночный режим. При расширяющемся окне данные до 2022 участвуют в обучении всех фолдов, добавляя шум вместо сигнала.

### Схема WalkForwardSplit

```
|<──── train (3000 баров) ────>|< gap >|<── val (500) ──>|< embargo >|
                                  (4)                         (4)
                        |<──── train (3000 баров) ────>|< gap >|<── val (500) ──>|< embargo >|
                                                          (4)                         (4)
```

- **Фиксированное обучающее окно** (`ML_WF_TRAIN_SIZE=3000`, ≈1.7 года): только актуальный рыночный режим.
- **Gap = lookahead** (`ML_LOOKAHEAD=4`): устраняет прямую утечку меток.
- **Embargo** (`ML_WF_EMBARGO=4`): метки последних барóв val зависят от 4 барóв за пределами val-окна. Без embargo эти бары войдут в следующее обучающее окно. Embargo равен lookahead — минимально достаточный размер.
- **Шаг фолда** = `val_size + embargo` = 504 бара: следующий train начинается после embargo, а не сразу после val.
- **Последние n_splits фолдов** (`ML_N_SPLITS=5`): только ближайшие к OOS периоду, данные из ~2.5 лет до конца обучения.

### Параметры

| Параметр | Переменная | Значение | Смысл |
|---|---|---|---|
| `train_size` | `ML_WF_TRAIN_SIZE` | 3000 | Обучающее окно, ≈1.7 года при 1h |
| `val_size` | `ML_WF_VAL_SIZE` | 500 | Val-окно, ≈3 месяца при 1h |
| `gap` | `ML_LOOKAHEAD` | 4 | Пропуск = lookahead (устраняет утечку меток) |
| `embargo` | `ML_WF_EMBARGO` | 4 | Пропуск после val = lookahead (устраняет обратную утечку) |
| `n_splits` | `ML_N_SPLITS` | 5 | Последние N фолдов |

### Fallback

Если данных тикера меньше `train_size + gap + val_size = 3504 баров` — используется один фолд 80/20 без gap/embargo. Это актуально для тикеров с короткой историей или при ночном дообучении с малым количеством новых данных.

### Почему не Purged K-Fold и не CPCV

- **Purged K-Fold (de Prado):** использует данные эффективнее, но требует отслеживания временных меток каждой метки — существенное усложнение кода. При нашем объёме данных (3000-7000 баров) и небольшом числе Optuna trials (25-75) разница в качестве оценки незначительна.
- **Combinatorial Purged CV (CPCV):** по [QuantBeckman](https://www.quantbeckman.com/p/with-code-combinatorial-purged-cross) требует "orders of magnitude more intensive" вычислений. При 25-75 Optuna trials добавление 100-1000 путей CPCV увеличит время HPO в 20-50 раз — неприемлемо на 2GB сервере.

`WalkForwardSplit` с gap и embargo — оптимальный баланс между корректностью оценки и вычислительной сложностью.

## Метрика оптимизации HPO (Spearman correlation)

Optuna HPO и CV-оценка ансамбля используют **среднюю корреляцию Спирмена** между `pnl_pred` и реальным P&L:

```
Spearman(pnl_pred, y) = корреляция рангов
```

**Почему не Sortino:** с ~88% отрицательных P&L-целей Sortino всегда отрицательный (BUY-сигналы в среднем убыточны),
что делает его неинформативным для ранжирования гиперпараметров. Spearman измеряет чистое качество ранжирования —
насколько порядок предсказаний соответствует порядку реальных P&L — без зависимости от порога входа.

**Диапазон:** [-1, 1]. Цель HPO — максимизировать. 0.0 = случайный прогноз, 0.1+ = уже значимо.

**Преимущества:**
- Не зависит от выбора порога BUY/SELL — чистая мера предсказательной силы
- Не требует P&L-симуляции в каждом фолде → быстрее в 3–5× (нет SL/TP цикла)
- Инвариантен к монотонным преобразованиям: масштаб предсказаний не важен
- Всегда информативен: даже при 88% отрицательных целей корреляция Спирмена осмысленна

**Оптимизация порога входа per-ticker** (отдельный этап, метрика — Sortino):
временный ансамбль обучается на 80% данных, персентиль `signal_pct ∈ [70, 95]` подбирается Optuna
на holdout 20% — абсолютный порог сохраняется в `best_threshold_{ticker}_{version}.json`. Без утечки.
Финальный ансамбль переобучается на 100% данных.

**P&L-симуляция** (`_simulate_pnl`) по-прежнему используется для оптимизации порога:
- Одна позиция за раз (нет перекрытия позиций)
- Вход: `close[t]` — цена закрытия свечи с BUY-сигналом
- Выход по приоритету: 1) SL, 2) TP, 3) SELL-сигнал **если позиция прибыльна**, 4) `close[t + lookahead]`
- P&L: `net = gross - 2×commission - max(0, (gross - 2×commission) × tax_pct)`

## Целевые P&L значения (compute_pnl_targets)

Вместо дискретных меток BUY/SELL/HOLD регрессор обучается на непрерывном **net P&L** каждого бара
(`compute_pnl_targets` в `ml/labels.py`):

```python
# Для каждого бара: симулируем BUY → выход по SL/TP/lookahead → считаем net P&L
entry      = close_window[:, 0]
# SL/TP триггеры в net-базисе (совпадают с adjusted_sl/tp_price в profitability.py):
sl_prices  = entry * (1 + c - sl_pct) / (1 - c)
tp_prices  = entry * ((1 + c) + tp_pct / (1 - t)) / (1 - c)
# P&L после комиссии и НДФЛ:
gross      = (exit_price - entry) / entry
net_pnl    = gross - 2*commission - max(0, (gross - 2*commission) * tax_pct)
```

**Что это даёт:**
- Нет дискретизации: непрерывный P&L полностью описывает доходность сделки
- Нет дисбаланса классов: регрессия не требует `class_weight="balanced"`
- Нет `ML_THRESHOLD` для меток: порог входа теперь оптимизируется в P&L-пространстве per-ticker
- Полное выравнивание между целью обучения и метрикой HPO (Spearman correlation)

`ML_THRESHOLD` в `.env` — fallback порог входа (предсказанный net P&L) для тикеров без `best_threshold_*.json`.

## Optuna HPO — настройки самплера и пруннера

Каждый раз при полном обучении (`--force-tune` или первый запуск) Optuna подбирает гиперпараметры трёх моделей.

### Самплер (TPESampler)

Байесовская оптимизация через Tree-structured Parzen Estimator. Первые `n_startup_trials` трайлов — случайный поиск,
после чего TPE строит суррогатную модель и предлагает перспективные точки.

| Модель | `n_startup_trials` | Итераций (`ML_OPTUNA_TRIALS_*`) |
|---|---|---|
| LightGBM | 25 (~2-3× кол-во параметров, 11 параметров) | `ML_OPTUNA_TRIALS_LGBM` = 75 |
| ExtraTrees | 15 (~2-3× кол-во параметров, 6 параметров) | `ML_OPTUNA_TRIALS_ET` = 40 |
| HistGradientBoosting | 15 (~2-3× кол-во параметров, 6 параметров) | `ML_OPTUNA_TRIALS_HIST_GBM` = 40 |
| Порог уверенности | 5 (1D задача) | `ML_THRESHOLD_N_TRIALS` = 50 |

### Пруннер (MedianPruner)

Досрочно останавливает трайлы, чья промежуточная корреляция Спирмена хуже медианы завершённых трайлов на том же шаге CV.
Значение после каждого фолда передаётся через `trial.report(score, step=fold_idx)`.

`n_startup_trials` пруннера совпадает с `n_startup_trials` самплера — иначе пруннер обрезает рандомные трайлы
до построения суррогатной модели TPE, уничтожая случайное исследование пространства.

| Параметр | LightGBM | ExtraTrees / HistGBM | Смысл |
|---|---|---|---|
| `n_startup_trials` | 25 | 15 | Пруннер не активен для первых N трайлов (нет медианы для сравнения) |
| `n_warmup_steps` | 2 | 2 | Первые 2 фолда CV всегда выполняются — Spearman корреляция накапливает достаточно данных |

## Ночное дообучение

Каждую ночь в `RETRAIN_HOUR:RETRAIN_MINUTE` (по `RETRAIN_TIMEZONE`) бот автоматически:

1. **Собирает новые свечи** — инкрементально, только с момента последней записи в БД
2. **Переобучает per-ticker ансамбли** — Optuna HPO пропускается (используется кеш `best_params_*.json`).
   `WalkForwardSplit` запускается с `n_splits=3` — метрика Spearman обновляется каждую ночь.
3. **Сбрасывает in-memory кеш** — следующий сигнал берётся из обновлённых весов
4. **Отправляет уведомление в Telegram** — список обученных тикеров и ошибок

Swap-thrashing устранён снижением `n_splits` до 3 и `n_jobs=1` везде.

**Оптимизация порога уверенности per-ticker:** после финального фита Optuna подбирает
`confidence_threshold` индивидуально для каждого тикера (50 трайлов, последние 20% данных).
Критерий — Sortino ratio P&L-симуляции: `_sortino_score(_simulate_pnl(...))`.
При менее `ML_SHARPE_MIN_TRADES` сделок возвращается 0.0 — штраф "молчаливым" моделям.
Результат сохраняется в `ml/weights/best_threshold_{ticker}_{version}.json`.
Scheduler загружает его вместо глобального `TRADING_CONFIDENCE_THRESHOLD`.
Настраивается через `ML_THRESHOLD_N_TRIALS` и `ML_SHARPE_MIN_TRADES`.

Настройки: `RETRAIN_ENABLED`, `RETRAIN_HOUR`, `RETRAIN_MINUTE`, `RETRAIN_TIMEZONE`, `RETRAIN_FORCE_TUNE` — см. [settings.md](settings.md#ночное-дообучение).

## Оптимизация памяти при обучении

Тикеры загружаются **последовательно** — по одному из PostgreSQL. В RAM одновременно
находятся данные только одного тикера. После завершения тикера память освобождается явно:

```python
del probe      # ансамбль прохода 1 после отбора признаков
del group      # свечи тикера после обучения
gc.collect()   # принудительный сбор
```

Кросс-валидация запускается с `n_jobs=1` — без форка процессов и копий X в RAM.
`RankEnsemble` — базовые модели обучаются последовательно, без параллельных fork.
`ExtraTreesRegressor(n_jobs=1)` — однопоточно, без внутренней параллелизации.

Ночное переобучение включает CV (n_splits=3) для актуализации метрики Spearman.
Optuna HPO пропускается — параметры берутся из кеша. Время обучения ~10–15 мин на 10 тикеров.

Это позволяет обучать все 27 тикеров на сервере с ограниченной оперативной памятью (2GB RAM).

## LRU-кеш моделей при инференсе

27 pkl-файлов моделей весят суммарно ~1.8 GB на диске и разворачиваются в ~3+ GB RAM
при одновременной загрузке. На сервере с 2 GB это вызывает swap-thrashing.

`ml/predict.py` использует **LRU-кеш** (`collections.OrderedDict`) с лимитом
`ML_MODEL_CACHE_SIZE` (по умолчанию `1`). Тикеры обрабатываются поочерёдно —
достаточно держать одну модель в RAM. При загрузке новой модели старая вытесняется:

```
predict_all([SBER, GAZP, ..., FEES]) — последовательно:
  загрузить SBER  → сигнал → вытеснить SBER
  загрузить GAZP  → сигнал → вытеснить GAZP
  ...
Пик RAM: ~100–130 MB (1 модель) вместо 3+ GB
```

Overhead на инференс: ~1–2 с на тикер (чтение pkl с диска) — незначим для часового цикла.

| `ML_MODEL_CACHE_SIZE` | RAM на модели | Когда использовать |
|---|---|---|
| `1` | ~100 MB | сервер 2 GB (рекомендуется) |
| `3` | ~300 MB | сервер 4+ GB |
| `27` | ~3+ GB | сервер 8+ GB |

## Последние результаты обучения

Обновляются автоматически в `ml/weights/last_results.json` после каждого обучения.
Метрика: **Spearman correlation** между pnl_pred и реальным P&L на CV.

Старые результаты (до марта 2026) недействительны — архитектура пересмотрена:
- **Март 2026 v1**: классификатор (BUY/SELL/HOLD) → Sortino HPO, симуляционные метки по gross
- **Март 2026 v2**: регрессор net P&L → Sortino HPO, `compute_pnl_targets`, нет class_weight,
  SELL-выход только при прибыльной позиции, `next_available = i + exit_j + 1`
- **Март 2026 v3**: HPO-метрика Sortino → Spearman (Sortino=-1.27 на 88% отрицательных целях
  неинформативен), `alpha` LightGBM тюнируется Optuna [0.7, 0.95], HistGBM добавлен в ансамбль
- **Март 2026 v4**: `VotingRegressor` → `RankEnsemble` с z-score нормализацией предсказаний
  перед усреднением; `min_impurity_decrease` ET на лог-шкале [1e-7, 1e-3];
  HPO на всех 54 признаках (деревья сами игнорируют слабые через регуляризацию)
- **Март 2026 v5**: 54 → 58 признаков: добавлены `autocorr_returns` (режим импульс/mean-reversion),
  `price_vol_corr` (подтверждение объёмом по WorldQuant alpha library), `williams_r` (TA-Lib WILLR,
  дополнительный momentum осциллятор), `cci_delta` (дельта CCI, аналогично rsi/stoch/macd дельтам).
  Все периоды настраиваются через `.env` (`ML_AUTOCORR_WINDOW`, `ML_PRICE_VOL_CORR_WINDOW`,
  `ML_WILLIAMS_R_PERIOD`, `ML_CCI_DELTA_PERIOD`). Требует переобучения (`--force-tune`).
