# ML-система

## Архитектура ансамбля

Для каждого тикера обучается отдельный `VotingClassifier(voting='soft')` — усреднение вероятностей.
Каждая базовая модель обёрнута в `Pipeline(StandardScaler)`:

```python
VotingClassifier(
    estimators=[
        Pipeline([("scaler", StandardScaler()), ("model", LGBMClassifier(...))]),
        Pipeline([("scaler", StandardScaler()), ("model", ExtraTreesClassifier(...))]),
    ],
    voting="soft",  # усреднение вероятностей, а не голосование классами
    n_jobs=1,       # последовательный фит базовых моделей — меньше RAM на слабом сервере
)
```

**Почему ExtraTrees, а не RandomForest:** ET использует случайные пороги разбиений вместо
поиска лучшего — корреляция с LightGBM значительно ниже, ансамбль получает реальное разнообразие.
RandomForest давал эффект хуже каждой модели по отдельности из-за высокой корреляции с LightGBM.

**Почему не SVC:** SVC (RBF) был протестирован, но дал F1=0.3831 — ниже обоих деревьев (~0.405).
В soft voting его плохо калиброванные вероятности (Platt scaling) тянули ансамбль вниз:
итоговый F1 ансамбля 0.3913 оказался хуже каждой модели по отдельности. SVC исключён.

`StackingClassifier` не подходит для временных рядов: его внутренний `cv=StratifiedKFold`
перемешивает данные → утечка будущего в OOF → мета-модель деградирует на честном `TimeSeriesSplit`.
Весь ансамбль сохраняется в одном `.pkl` файле.

> **Важно:** после изменения набора признаков (`features.py`) или структуры ансамбля
> необходимо запустить `python -m scripts.train_model --force-tune` —
> Optuna подберёт гиперпараметры под новый набор признаков.

## Per-ticker отбор признаков

Обучение проходит в **два прохода**:

1. **Проход 1** — быстрый `fit` ансамбля на всех 52 признаках. Вычисляется нормализованная
   importance для каждой модели (LightGBM и ExtraTrees независимо нормализуются к сумме = 1,
   затем усредняются; SVC не имеет `feature_importances_` и пропускается). Признаки с
   `avg_importance < ML_FEATURE_IMPORTANCE_THRESHOLD` отбрасываются.

2. **Проход 2** — оптимизация порога уверенности (Optuna, без утечки) и финальный `fit` только на отобранных признаках.
   Список признаков сохраняется в `features_{ticker}_{version}.json`.

Каждый тикер получает **свой** набор признаков:

```
features_SBER_v2.json  → ["OBV", "cmf_20", "vwap_ratio", ...]   # 32 признака
features_LKOH_v2.json  → ["high_252_ratio", "MACD_hist", ...]   # 40 признаков
features_YDEX_v2.json  → ["hist_vol_20", "donchian_pct", ...]   # 37 признаков
```

Инференс загружает `features_{ticker}_{version}.json` автоматически — изменений в коде не требуется.

## Метрика оптимизации (Sortino ratio)

Вместо F1-macro Optuna HPO и CV-оценка ансамбля используют **Sortino ratio P&L-симуляции**:

```
Sortino = mean(P&L) / downside_std(P&L)
```

где `downside_std` — стандартное отклонение только убыточных сделок.
В отличие от Sharpe не штрафует за случайный крупный выигрыш: высокая прибыль не увеличивает знаменатель.
Для торговой системы с ограниченными потерями (SL) и несимметричными выигрышами (TP) теоретически корректнее Sharpe.

**Симуляция сделок** (`_simulate_pnl`):
- Одна позиция за раз (нет перекрытия позиций)
- Вход: `close[t]` — цена закрытия свечи с BUY-сигналом
- Выход: первая свеча, задевшая SL или TP (в пределах `ML_LOOKAHEAD` свечей), иначе `close[t + lookahead]`
- P&L сделки — точная реплика торговой логики планировщика:
  ```
  gross      = (exit - entry) / entry
  commission = 2 × commission_pct
  tax        = max(0, (gross - commission) × tax_pct)   # НДФЛ только на прибыль
  net        = gross - commission - tax
  ```
- HOLD и SELL сигналы не создают сделок

**Преимущества перед F1:**
- Напрямую моделирует торговую прибыльность, а не качество классификации
- Учитывает НДФЛ — симуляция калибруется к реальной доходности, не к завышенной
- Штрафует только убыточную волатильность (downside), не трогает прибыльную
- Штрафует "молчаливые" модели: при < `ML_SHARPE_MIN_TRADES` сделок → возвращает 0.0

**CV-метрика использует `predict_proba()[:, 2] >= 0.5`** вместо `predict()` (argmax):
`predict()` с balanced-классами выдаёт BUY на ~33% баров → ложные сделки → Sortino < 0.
Порог 0.5 означает «модель считает BUY вероятнее SELL+HOLD вместе взятых» — ближе к продакшн-логике.

**Оптимизация порога уверенности per-ticker** выполняется **до** финального фита:
временный ансамбль обучается на 80% данных, порог подбирается Optuna на holdout 20% — без утечки.
Затем финальный ансамбль переобучается на 100% данных.

## Симуляционные метки (create_labels_sim)

Метки генерируются той же SL/TP-симуляцией что и HPO-метрика (`create_labels_sim` в `ml/labels.py`):

```
gross > +threshold  →  BUY  (2) — цена выросла достаточно
gross < -threshold  →  SELL (0) — цена упала достаточно
иначе               →  HOLD (1)
```

Метки определяются по **gross** (сырой доходности), а не по `net_pnl`.
Комиссия 0.6% в знаменателе net_pnl сдвигала SELL-зону вправо: любое падение даже на 0.1%
давало SELL → дисбаланс >60% SELL / 4% BUY. Комиссия и налог учтены в Sortino HPO-метрике — не в метках.

**Что это даёт:** устраняет рассогласование между целью обучения и целью оптимизации.
Раньше модель училась предсказывать сырую доходность через `lookahead` свечей,
а HPO оценивал её по SL/TP-исходу — это разные события. Теперь метка BUY означает
«цена выросла на >threshold% из этой точки» — направление которое Sortino-метрика вознаграждает.

`ML_THRESHOLD` задаёт минимальное **gross** движение цены для получения метки BUY/SELL (например, 0.005 = 0.5%).

## Ночное дообучение

Каждую ночь в `RETRAIN_HOUR:RETRAIN_MINUTE` (по `RETRAIN_TIMEZONE`) бот автоматически:

1. **Собирает новые свечи** — инкрементально, только с момента последней записи в БД
2. **Переобучает per-ticker ансамбли** — флаг `--skip-cv`: только финальный фит без CV.
   Optuna HPO пропускается (используется кеш `best_params_*.json`).
   F1-метрики сохраняются из предыдущего обучения (CV не запускается → нули не записываются).
3. **Сбрасывает in-memory кеш** — следующий сигнал берётся из обновлённых весов
4. **Отправляет уведомление в Telegram** — список обученных тикеров и ошибок

**Ночное обучение включает CV** (n_splits=3) — метрика Sortino обновляется каждую ночь.
Swap-thrashing устранён снижением `n_splits` до 3 и `n_jobs=1` везде.

**Оптимизация порога уверенности per-ticker:** после финального фита Optuna подбирает
`confidence_threshold` индивидуально для каждого тикера (50 трайлов, последние 20% данных).
Критерий — Sortino ratio P&L-симуляции: `_sortino_score(_simulate_pnl(...))`.
При менее `ML_SHARPE_MIN_TRADES` сделок возвращается 0.0 — штраф "молчаливым" моделям.
Результат сохраняется в `ml/weights/best_threshold_{ticker}_{version}.json`.
Scheduler загружает его вместо глобального `TRADING_CONFIDENCE_THRESHOLD`.
Настраивается через `ML_THRESHOLD_N_TRIALS` и `ML_SHARPE_MIN_TRADES`.

Настройки: `RETRAIN_ENABLED`, `RETRAIN_HOUR`, `RETRAIN_MINUTE`, `RETRAIN_TIMEZONE`, `RETRAIN_FORCE_TUNE` — см. [settings.md](settings.md#ночное-дообучение).

## Оптимизация памяти при обучении

Тикеры загружаются **последовательно** — по одному из PostgreSQL. В RAM одновременно
находятся данные только одного тикера. После завершения тикера память освобождается явно:

```python
del probe      # ансамбль прохода 1 после отбора признаков
del group      # свечи тикера после обучения
gc.collect()   # принудительный сбор
```

Кросс-валидация запускается с `n_jobs=1` — без форка процессов и копий X в RAM.
`VotingClassifier(n_jobs=1)` — базовые модели обучаются последовательно, без параллельных fork.
`ExtraTreesClassifier(n_jobs=1)` — однопоточно, без внутренней параллелизации.

При ночном переобучении CV полностью пропускается (`--skip-cv`) — время обучения ~3 мин
на 10 тикеров вместо потенциального зависания от swap-thrashing.

Это позволяет обучать все 10 тикеров на сервере с ограниченной оперативной памятью (2GB RAM).

## LRU-кеш моделей при инференсе

10 pkl-файлов моделей весят суммарно ~670 MB на диске и разворачиваются в ~1.1 GB RAM
при одновременной загрузке. На сервере с 2 GB это вызывает swap-thrashing.

`ml/predict.py` использует **LRU-кеш** (`collections.OrderedDict`) с лимитом
`ML_MODEL_CACHE_SIZE` (по умолчанию `1`). Тикеры обрабатываются поочерёдно —
достаточно держать одну модель в RAM. При загрузке новой модели старая вытесняется:

```
predict_all([SBER, GAZP, ..., YDEX]) — последовательно:
  загрузить SBER  → сигнал → вытеснить SBER
  загрузить GAZP  → сигнал → вытеснить GAZP
  ...
Пик RAM: ~100–130 MB (1 модель) вместо 1.1 GB
```

Overhead на инференс: ~1–2 с на тикер (чтение pkl с диска) — незначим для часового цикла.

| `ML_MODEL_CACHE_SIZE` | RAM на модели | Когда использовать |
|---|---|---|
| `1` | ~100 MB | сервер 2 GB (рекомендуется) |
| `3` | ~300 MB | сервер 4+ GB |
| `10` | ~1.1 GB | сервер 8+ GB |

При запуске `python -m scripts.train_model` прогресс отображается в терминале:

```
========================================================
  [1/10] SBER  (21480 строк)
========================================================
    LightGBM HPO   [из кеша]
    ExtraTrees HPO [из кеша]
    Отбор признаков [из кеша]
    CV оценка   [пропущена — skip_cv]          ← при ночном запуске
  > Финальное обучение ансамбля... ok
  Сохранено: ensemble_SBER_v2.pkl

  ИТОГ: 10/10 тикеров обучено
    + SBER     -> ensemble_SBER_v2.pkl

    + MTSS     -> ensemble_MTSS_v2.pkl
```

Чтобы увидеть таблицу важности признаков после каждого тикера — установить `ML_PRINT_FEATURE_IMPORTANCE=true` в `.env`.

Гиперпараметры кешируются в `ml/weights/best_params_{model}_{ticker}_{version}.json`.
При повторном запуске без `--force-tune` HPO пропускается — используется кеш.

## Последние результаты обучения

Обновляются автоматически в `ml/weights/last_results.json` после каждого обучения.
Метрика: **Sortino ratio** P&L-симуляции на CV (вместо F1 — метрика изменена в марте 2026).

Предыдущие результаты с F1 недействительны — метка и метрика были пересмотрены:
- Метки: `gross > threshold` вместо `net_pnl > threshold` (убрана асимметрия от комиссии)
- Метрика HPO: Sortino P&L-симуляции вместо F1-macro
- CV: `predict_proba >= 0.5` вместо `predict()` (argmax)
- Порог: оптимизируется до финального фита (без data leakage)
